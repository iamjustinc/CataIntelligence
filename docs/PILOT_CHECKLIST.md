# Pilot checklist: backup, restore and readiness

A pilot with real users and real catalog data should not start until every item in sections 1 to 3 is ticked by the person named beside it. Nothing below has been done for a hosted environment; section 1 has been verified locally only, as noted.

## 1. Backup and restore

The database is the system of record: decisions, releases and the audit trail exist nowhere else. Uploaded files and exports can be regenerated or re-uploaded; the database cannot.

| Step | How | Status |
| --- | --- | --- |
| Logical backup | `pg_dump --format=custom --no-owner --file=backup.dump "$DATABASE_ADMIN_URL"` as the owner role | Verified locally by `pnpm backup:check` |
| Restore into an empty database | `createdb <name>`, then `pg_restore --no-owner --dbname=<name> backup.dump`, then `pnpm db:migrate` against it to recreate the application role's grants | Verified locally by `pnpm backup:check` |
| Verify the restore | Row counts of every table equal the source; the same tables have row-level security and the same policies; the append-only triggers still refuse an update; the application role sees no rows without a workspace | Verified locally by `pnpm backup:check` |
| Application starts on the restored database | Point a web process at it; sign in; the dashboard totals equal the source | **Not done** |
| Scheduled backups with retention | Platform feature or a cron job; decide frequency and retention | **Not done** |
| Point-in-time recovery | WAL archiving or a managed database's equivalent | **Not done** |
| Restore drill on the hosted environment, timed | Record how long it takes and who can do it | **Not done** |
| Storage directory backup | Only needed if staged imports or exports must survive loss; exports can be regenerated byte-for-byte from a release | **Decision needed** |

`pnpm backup:check` dumps a source database (read-only), restores it into a scratch database named `<source>_restorecheck`, compares it and drops the scratch database. It never writes to the source. By default the source is the development database.

Keep `BETTER_AUTH_SECRET` with the backup's custodian: a restored database with a different secret signs everyone out but loses no data.

## 2. Security and data handling

- [ ] HTTPS only; `APP_BASE_URL` is the HTTPS origin. *(operator)*
- [ ] Web and worker use the application role. The owner URL exists only where migrations run. *(operator)*
- [ ] Seeded demo identities are absent or their password is changed; `SEED_USER_PASSWORD` is not a known value. *(operator)*
- [ ] Provider retention and training terms reviewed for the key's account before any real catalog is sent. *(data owner)*
- [ ] Merchant permission to process their catalogs, including by an AI provider, is recorded. *(data owner)*
- [ ] Who may be an administrator is decided; members are added in the database until a member screen exists. *(product owner)*
- [ ] A retention period for committed data is agreed. The application deletes uncommitted uploads after 24 hours and export files after 7 days; it never deletes committed data, and workspace deletion is not built. *(data owner)*
- [ ] An independent security review. The automated suite checks role and workspace isolation on every API route; it is not a penetration test. *(security)*

## 3. Product readiness for the pilot's purpose

- [ ] Live AI verified: `pnpm smoke:live` passes with the pilot's key and model, and one live job has been run and reviewed. **Not done: no credentials were available during development.**
- [ ] Budgets and prices entered in Settings; someone owns watching spend.
- [ ] The pilot taxonomy is loaded and its definitions are reviewed by its owner. Weak definitions produce plausible, inconsistent mappings (PRD section 20).
- [ ] Reviewers understand that suggestions are proposals, that Medium and Low are review priorities and not probabilities, and that High is disabled.
- [ ] Accessibility: a manual pass with a screen reader on review and analytics. Automated checks pass; they cover only part of WCAG 2.2 AA.
- [ ] Someone is on call for the worker during pilot hours; nothing alerts automatically.
- [ ] Usability sessions (KPI08) and the review-time study (KPI04) are scheduled if the pilot is meant to measure them (`evals/PROTOCOL.md`, section 8).

## 4. What a pilot can and cannot conclude

It can show whether the workflow fits how the team works, where reviewers stall, and how often suggestions are corrected. It cannot establish suggestion accuracy or justify enabling High: that needs the frozen evaluation in `evals/PROTOCOL.md`, with expert labels.
